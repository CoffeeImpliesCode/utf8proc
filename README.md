# utf8proc — Zig SDK fork

A Zig 0.16 package that compiles the upstream C library **utf8proc 2.12.0**
(Unicode 18.0.0) from the sources in this repository and publishes a typed Zig
facade over it, the complete raw C route, and a build that works linked,
installed and cross-compiled.

Upstream is `JuliaStrings/utf8proc`, pinned at
`79cdd5ab40c79afa559f689ffc13b76812dee1ac` (tag `v2.12.0`). Upstream's own README
is carried, byte for byte, as [`README.upstream.md`](README.upstream.md) — this
file is the fork's. Nothing upstream wrote was edited; see
[upstream provenance](UPSTREAM.md).

**This package is local and unpublished.** No repository was created, no remote
was touched, and nothing here is authorized for publication.

Two independent measurements say so, and both are the driver's, from 2026-10-03

* `sha256sum -c UPSTREAM.sha256` — 56 records, 56 `OK` lines. That record pins
  every carried upstream byte and all six `testdata/` files, and the README

* Every carried upstream path re-derived from the pinned commit's own git blob,
  matched against the driver's 53-blob archive map, with differences exactly
  `.gitignore`, `build.zig`, `build.zig.zon` — the three files edited in place.

Nothing native is patched, generated, vendored, substituted or omitted. The one

**Build options this SDK defines.** `-Dlinkage=static|dynamic` selects the
delivered artifact and defaults to `static`, which is upstream's own policy. The
shared delivery carries upstream's own ABI version — `Makefile:25-27`'s `3.3.0`,
which `utf8proc.h:66-68` distinguishes from the API version — and is installed as
`libutf8proc.so.3.3.0` with soname `libutf8proc.so.3` and a `libutf8proc.so`
link on ELF, `libutf8proc.3.3.0.dylib` with install name `libutf8proc.3.dylib` on
Darwin, and `utf8proc.dll` with its import library on Windows, where a DLL has
no soname. `utf8proc_utf8class[256]` is exported from the shared object alongside
the functions, because the shared compile line carries `-DUTF8PROC_EXPORTS`.

`-Dlinkage=dynamic` is a claim that the target can load a shared object, and a
target whose OS has no dynamic linker cannot: there the build stops with the
triple, the OS tag and the reason rather than handing back a static archive
instead. A substitution the caller did not ask for is a build that answered a
different question and reported success, so the static default is untouched and
`wasm32-wasi` with no linkage flag is an ordinary static archive.

`-Druntime=true` selects runtime dispatch, defaults to `false` and is orthogonal
to linkage. Under it the facade's `c` import becomes a generated dispatch built
by the API role's `runtime/graph.zig`, and **no native library is linked into the
module at all** — neither the library this tree builds nor an installed one. The
library is still built and installed, so a caller may name a provider this tree
did not build. A linked build is unchanged: `c` is the translated header itself
and `load` stops the program with a message rather than quietly succeeding, so a
consumer supporting both configurations can tell them apart at comptime through
`runtime_loaded`. Eight runtime-loaded cells in epoch
`20261004T232823091897Z-23133` have since observed that dispatch against this
tree's own source-built provider; the failure, retry, provider-change and
pre-load-panic behaviours still have no receipt. See
[the matrix](#build-run-and-test-matrix).

## Consumption

### Zig, linked

```zig
// build.zig.zon of a dependent
.dependencies = .{ .utf8proc = .{ .url = "…", .hash = "…" } },

// build.zig of a dependent
const utf8proc = b.dependency("utf8proc", .{ .target = target, .optimize = optimize });
exe.root_module.addImport("utf8proc", utf8proc.module("utf8proc"));
```

The module publishes the typed facade as its own declarations and the complete
raw route as `pub const c`. Both are the supported ways in; the raw route is not
a second-class path. The interface, every owned precondition, the error set and
the boundaries upstream does not guarantee are documented separately in
[`README.zig.md`](README.zig.md) — read that before calling anything.

A path dependency on this directory works and needs no packaging:

```zig
dep.module("utf8proc", .{ .path = "../utf8proc" })
```

### C

`include/utf8proc.h` is upstream's header, unchanged. A C consumer compiles
against it and links `-lutf8proc`, statically or against the shared library.
The one macro a consumer must get right is `UTF8PROC_STATIC` for a static link:
`utf8proc.h:123-139` turns it into an empty export macro, while without it a
Windows consumer declares every function `__declspec(dllimport)`. That is what
the installed `lib/pkgconfig/libutf8proc.pc` encodes per variant — the build graph
generates it from upstream's own template, and it is the one place this SDK
departs from that template: upstream ships `-DUTF8PROC_EXPORTS`, which is the
macro for *building* the library, not for using it. Upstream's templates are
untouched on disk and stay hashed; see [`NOTICE.md`](NOTICE.md) and
`UPSTREAM.md`.

### Nix

One source-only derivation, `package.nix`, with `linkage` selecting the variant;
the entry points name it.

```sh
nix build ".#static"     # lib/libutf8proc.a — the SDK's own policy, and default
nix build ".#shared"     # lib/libutf8proc.so — real -Dlinkage=dynamic
```

Each output is written entirely by the build graph: `include/utf8proc.h`,
`lib/libutf8proc.a` or, under `-Dlinkage=dynamic`, `lib/libutf8proc.so.3.3.0`
with soname `libutf8proc.so.3` and a `libutf8proc.so` link,
`lib/pkgconfig/libutf8proc.pc`, `LICENSE.md` at the root,
`share/licenses/utf8proc/{LICENSE.md,FORK-LICENSE.md,NOTICE.md,UPSTREAM.md,CHANGELOG.md,Unicode-License-V3.txt}`
and `share/utf8proc/testdata/` with the five Unicode corpora. The `.pc` is
relocatable — `prefix=${pcfiledir}/../..` — so a staged or packed tree still
describes itself. The derivation adds nothing to that closure, fetches nothing,
downloads nothing at build time, and passes no C flags: the build graph owns those.
Build it from the working tree with `path:$PWD` until this
copy is committed, because a flake evaluated from a git checkout carries only
committed files.

**The flake's lock is here, and it is the driver's.** `flake.lock` was written
into this tree on **2026-10-04**, after the five delivery files it belongs to.
It is the resolved form of the one input `flake.nix:15` declares — the same
`c7def046b9a883d46974757852106483d741586f` — plus the `narHash` for those bytes,
so it is not a second answer to the input it resolves. It travels in `.paths`
because `.gitignore:82-85` records that a lock is a real input and that
ignoring one is the wrong way to keep it out of a commit, and because the
closure is compared in both directions: a file that is neither listed in
`.paths` nor named in `verify.yml`'s carried-not-shipped list is a closure
failure. Nothing here claims its terms — it is the driver's file, inventoried as
such in [`NOTICE.md`](NOTICE.md) and excluded from the fork's MIT grant in
[`FORK-LICENSE.md`](FORK-LICENSE.md). There is still **no `devenv.lock`**, and
`devenv.yaml:19-22` says why.

**`static` means a static library artifact.** Nothing here promises a wholly
static executable or a fully static closure; libc is still linked by whatever
uses the result.

### devenv

devenv is the canonical development interface; the flake is the portable
alternative. The shell carries tools only, plus both package variants as lazy
outputs:

```sh
devenv shell
# scripts: sdk-build sdk-test sdk-smoke sdk-exercise sdk-check
#          sdk-upstream-test sdk-consumer sdk-integrity sdk-format
# packages: devenv build outputs.static | devenv build outputs.shared
```

**Every script locates this SDK itself**, so the directory devenv was started
from does not matter: `devenv shell -- sdk-consumer` and
`devenv shell -- sdk-integrity` work from a project directory that is not this
checkout. The nine names are unchanged; what each one runs now begins with a
`cd` to this directory, resolved from `devenv.nix`'s own location rather than
from an environment variable that names wherever the shell happened to be
entered.

**`sdk-consumer` forwards the selection you made, not the one this machine
happens to be.** The consumer step runs `consumer/` as its own `zig build` and
passes `-Dtarget` and `-Dcpu` down as the *query* it resolved — the literal
`native` when the selection named nothing, and the named arch, OS, ABI and CPU
otherwise. That is what keeps the nested build on this host's real dynamic
linker, which under Nix is a store path, instead of re-resolving a same-architecture
triple against the ABI defaults and asking for `/lib64/ld-linux-x86-64.so.2`,
which no Nix host has. An explicitly named cross target stays an explicit cross
target, and nothing on this path sets `skip_foreign_checks`. See
`CHANGELOG.md` entry 53.

**`build.zig`'s `runConsumer` writes the rest of that nested command line.**
It forwards `-Doptimize`, `-Dlinkage` and `-Druntime`, the `-f…` executor
switches and `--libc-runtimes` when this graph has them, and then `-j8` and
`--summary all`.

Two caches follow. The local one is `--cache-dir <outer>/consumer`, because two
graphs must not write one manifest directory, and it is sent only when
`b.cache_root.path` is set. The global one is `--global-cache-dir` followed by
whatever `b.graph.global_cache_root.path` resolves to, whole and unsuffixed,
because it is the package store both graphs read rather than a per-graph manifest
directory. An absent path is not invented, and the nested build then resolves
its own. `--prefix` is sent with this invocation's own `b.install_prefix`, made
absolute, whenever the caller named one. A relative value would otherwise
resolve against `consumer/`. With no prefix named, nothing is sent.

The caller's own arguments come last and behind `--`, and `consumer/build.zig`
hands the same arguments to its `run_exe`. A trailing `-- --provider <path>`
therefore reaches the consumer program rather than stopping at the nested
build. The step sets `has_side_effects`, so a repeated run whose inputs did not
change still runs the program. See `CHANGELOG.md` entries 54 and 55.

**Every `zig build` body names both caches explicitly.** One shared flag string
in `devenv.nix` gives all seven `--cache-dir "$ZIG_LOCAL_CACHE_DIR/utf8proc"
--global-cache-dir "$ZIG_GLOBAL_CACHE_DIR" -j8 --summary all`. `--cache-dir` is
explicit because Zig's own default is `.zig-cache` inside this checkout, and
this checkout is the working tree `UPSTREAM.sha256` and the driver's source
digest cover. Those flags are also what make `runConsumer`'s two cache relays
real: `b.cache_root.path` and `b.graph.global_cache_root.path` are optional
captures, so an entry that named neither would leave both to the nested build.

**A cache variable the caller did not export is filled; an all-empty one is
refused.** A non-empty `ZIG_LOCAL_CACHE_DIR` or `ZIG_GLOBAL_CACHE_DIR` from the
caller is used unchanged. A missing one is filled from `XDG_CACHE_HOME` first
and `TMPDIR` second, as `zig-local-cache` and `zig-global-cache`. When both are
still empty, the script names what is missing and exits non-zero before the
compiler runs. The fill is in each script body and not only in `enterShell`,
because a devenv script is a program that inherits the caller's environment, so
nothing the shell hook exported is guaranteed when a body starts. No fallback
is `/tmp`, `/var/tmp`, an NFS mount or a path inside this repository.

**`sdk-build` installs beneath that local cache directory**, at
`$ZIG_LOCAL_CACHE_DIR/utf8proc/zig-out`, and nowhere else. The other eight
scripts name no prefix of their own: `build.zig` keeps the smoke program and the
API exercise out of the installed prefix on purpose, and the consumer step adds
nothing to it either. `runConsumer` sends `run` when this host can execute the
resolved target and `install` when it cannot. With no prefix named it relays
none, so a `run` writes nothing outside its own cache and an `install` writes
only into `consumer/zig-out/`, which `.gitignore` already ignores.

`.envrc` names `XDG_RUNTIME_DIR` when the caller has named an approved scratch
root, because devenv otherwise defaults its runtime sockets to `/tmp` even when
`TMPDIR` is set. Entering the shell builds nothing: the SDK is reachable through
`outputs`, not `packages`.

### Runtime loading

Under `-Druntime=true` the module publishes `load`, `loadedSource`, `LoadSource`
and `LoadError` itself, so the caller names the failure it is handling rather
than reaching into a loader. `LoadSource` is `.path` for an explicit file or
`.system` for an explicit name for the platform loader; there is no
path-to-system fallback and no implicit second source. One process-lifetime table
per configured module: it is published once and atomically after every symbol is
bound, a failed attempt publishes nothing, a retry is explicit, the same request
again succeeds and changes nothing, a different request after a success is
`ProviderMismatch` and leaves the library in use alone, and a call from the thread
running the attempt is `ReentrantLoad` rather than a deadlock. The handle and the
loader's own copy of the request live to process exit; there is no owning library
object, no returned view, no unload and no reset. Calling a module function
before a successful load is an ordinary panic in every optimization mode.

**What a provider must be.** Every entry point `utf8proc.h` declares — the
thirty-one functions of `utf8proc.h:460-808` and the one exported object — with no
conditional entry point left to judgement, because no macro in that header gates a
declaration: each one is an option-word enumerator, a negative error code, a
version macro or an export macro. The authoritative list of what *was* routed is
the generated dispatch's own `symbols` array for the target being built, not a
hand-written copy.

**How a resolved provider is checked.** `validate` resolves nothing; it *calls*
five resolved entry points and *reads* the resolved data object through the exact
field types the translated header declares, and requires the answers the Unicode
standard fixes. A pointer whose calling convention, argument widths or
data-object element width differ cannot produce them. That is an ABI check, not a
compatibility claim, and `README.zig.md` is where the boundary is written down
precisely.

utf8proc's own declarations decide five things any such route must honour, and
they are facts about this library rather than about any implementation:

* **Exported data is one array, and it must be reached by address.**
  `utf8proc_utf8class[256]` (`utf8proc.h:453`, defined at `utf8proc.c:56`) is the
  only exported data symbol in the library. The six tables in `utf8proc_data.c`
  — including `utf8proc_properties[]`, which `utf8proc_get_property` returns
  pointers into — are `static const` and are **not** exported. A route that
  copied a table instead of taking its address in the loaded image would read a
  different array from the one the provider uses, and property-pointer identity
  is per-image by construction: comparing one against another across a provider
  boundary means nothing.
* **The allocator belongs to the image that allocated.** `utf8proc_map` allocates
  with the library image's `malloc` and `realloc` (`utf8proc.c:789-811`) and
  `utf8proc_free` calls that image's `free` (`utf8proc.c:848-849`). A buffer
  returned by a provider must therefore be released by **that provider's own
  `utf8proc_free`**, and host memory must never be freed through a loaded
  image. This is a provider constraint, not an implementation detail, and it
  applies equally to a `utf8proc_custom_func` result.
* **That is a same-allocator requirement, not a claim of Windows CRT
  interchange.** On Windows a host executable and a loaded DLL may resolve
  different C runtimes and therefore different heaps. Nothing in this package
  verifies, negotiates or guarantees that condition, and no route should be
  described as if it did: the crossing is safe only when both images really do
  resolve one allocator. On ELF targets the same discipline applies across a
  `dlopen`-ed image, where the bound symbols are the ones that image resolved.
* **Scalars and layout are fixed-width but not universal.** `utf8proc_int8_t`
  through `utf8proc_int32_t` are exact-width (`utf8proc.h:111-115`),
  `utf8proc_size_t`/`utf8proc_ssize_t` are `size_t`/`ptrdiff_t`
  (`utf8proc.h:117-118`) and `utf8proc_bool` is C `bool` — so a 32-bit and a
  64-bit provider differ in `ssize_t`, and `utf8proc_ssize_t` at 32 bits is the
  width that overflows first.
* **Symbol presence is not ABI identity.** 2.12.0 changed two declared types
  without a version bump that would catch it — `options` went from an `enum` to
  `unsigned int`, and `utf8proc_decompose_char`'s `last_boundclass` from `int *`
  to `utf8proc_int32_t *`. A provider has to be checked against the header it
  was built from, not merely found by `dlsym`/`GetProcAddress`. The
  `utf8proc_version()` string is the cheap half of that check and
  `UPSTREAM.md`'s system-library section records the rest.
* **A provider must carry the same Unicode version as this build's tables.**
  `utf8proc_get_property` indexes `utf8proc_stage1table` with the property's own
  `lower` and `upper` fields and with `codepoint >> 15` (`utf8proc.c:233-240`), so
  a provider built from a different Unicode revision can resolve every symbol,
  pass every ABI check and still answer differently about codepoints this build
  never asked about. This is the one requirement that is not about the C ABI at
  all, and it is why `validate` asks for the Unicode version to be present rather
  than for any particular value.

Linked and native calls remain supported exactly as before.
